---
title: Outgoing Webhooks
description: Pleep calls your endpoint when a lead moves stage in the funnel or a deal moves stage in your CRM
---

Outgoing webhooks let you stop polling the API and receive events as they happen. Pleep sends a `POST` with JSON to your HTTPS endpoint and signs every request.

<Callout title="Not the same as inbound webhooks">
  Inbound webhooks are an external system calling Pleep to wake the agent in a conversation. This is the opposite: Pleep calls you.
</Callout>

## Setup

Open [Settings → Developers](https://app.pleep.app/settings/developers) and find the "Outgoing webhooks" section. Give the endpoint a name, an HTTPS address, and the events you want. The signing secret is shown once on save — store it, it is never displayed again.

The same section shows the last 20 delivery attempts with response code, body and error text, and lets you disable an endpoint or rotate its secret.

## Events

| Event | When it fires |
|-------|---------------|
| `lead.status_changed` | A lead moved to another stage of the Pleep funnel. Fires whoever moved it: the AI agent, an operator in the UI, a scenario, or a [`set-status`](/en/api/leads) call |
| `crm.status_changed` | A deal or lead moved stage in an external CRM: amoCRM or Bitrix24 |

<Callout type="warn" title="crm.status_changed needs a connected external CRM">
  This event relays changes from amoCRM or Bitrix24. If you run your funnel inside Pleep and no external CRM is connected, it will never fire. Subscribe to `lead.status_changed` for the Pleep funnel.
</Callout>

## Request format

### Headers

| Header | Description |
|--------|-------------|
| `X-Pleep-Event` | Event name |
| `X-Pleep-Delivery` | Event id, same as the `id` field in the body |
| `X-Pleep-Timestamp` | Send time, unix seconds |
| `X-Pleep-Signature` | Signature, `sha256=<hex>` |

### Envelope

Every event shares one envelope; the payload lives in `data`.

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Event id. Stable across retries — dedupe on it |
| `event` | string | Event name |
| `occurred_at` | string | Event time (ISO 8601) |
| `application_id` | string | Application id |
| `data` | object | Payload, shape depends on the event |

### lead.status_changed

```json
{
  "id": "6f1c9a2e-4b55-4a1e-9f0d-2b7c1d3e4f50",
  "event": "lead.status_changed",
  "occurred_at": "2026-08-21T10:00:00.000Z",
  "application_id": "7dbbac93-00db-46a7-be99-9fc45d3a705d",
  "data": {
    "thread_id": "thread_0765c2bd-980d-4c65-aeea-d04069646be5",
    "assistant_id": "6cc47669-8659-40ad-9d4d-bf914323120d",
    "phone": "77051234567",
    "channel": "WABA_COEXISTENCE",
    "from": { "id": "7f3a1c20-…", "name": "Visit booked", "kind": "active" },
    "to":   { "id": "9c8b7a60-…", "name": "Won", "kind": "success" },
    "changed_by": "AI"
  }

```

| Field | Type | Description |
|-------|------|-------------|
| `thread_id` | string | Conversation id, the same one [`get-threads`](/en/api/get-threads) returns and the monitor link carries |
| `phone` | string \| null | Customer phone, when the channel has one |
| `from` | object \| null | Stage the lead left. `null` when it had none |
| `to` | object \| null | New stage. `null` when the stage was cleared |
| `changed_by` | string \| null | Who moved it: `AI`, `OPERATOR`, `SCENARIO`, `SYSTEM` or `VERIFIED_OUTCOME` |

```json
    "thread_id": "thread_0765c2bd-980d-4c65-aeea-d04069646be5",
    "assistant_id": "6cc47669-8659-40ad-9d4d-bf914323120d",
    "provider": "amocrm",
    "entity_type": "lead",
    "entity_id": "4242",
    "pipeline_id": "77",
    "from_status_id": "141",
    "to_status_id": "142",
    "contact_phone": "77051234567"

```

<Callout title="thread_id can be null">
  A lead typed into the CRM by hand or imported from a spreadsheet has never written to you, so it has no conversation. That is expected, not an error: `thread_id` is `null` and `contact_phone` is the only handle on the person. Your handler must allow for it.
</Callout>

## Verifying the signature

The signature is an HMAC-SHA256 of `${timestamp}.${body}`, where `timestamp` is the `X-Pleep-Timestamp` header and body is the **raw request bytes**.

<Callout type="warn" title="Verify against the raw body">
  Parsing the JSON and re-serializing it changes key order and whitespace, so the signature will not match. This is the most common integration mistake. Compute the signature before parsing.
</Callout>

The timestamp is signed along with the body, so a captured request cannot be replayed later: compare `X-Pleep-Timestamp` against your own clock and reject anything too old.

```js
const crypto = require('node:crypto');

function verify(rawBody, headers, secret) {
  const ts = headers['x-pleep-timestamp'];
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false;

  const mac = crypto
    .createHmac('sha256', secret)
    .update(`${ts}.${rawBody}`)
    .digest('hex');

  const expected = Buffer.from(`sha256=${mac}`);
  const received = Buffer.from(headers['x-pleep-signature'] ?? '');
  if (expected.length !== received.length) return false;
  return crypto.timingSafeEqual(expected, received);
}
```

## Retries

Any response outside `2xx`, plus timeouts and network errors, is retried. Up to **5 attempts** with a growing delay. A single request times out after 10 seconds.

Answer `2xx` immediately and move heavy work to your own queue. Your handler must be idempotent on `id`: a retry carries the same one.

Every attempt is written to the delivery log in the UI, so both the response code and your error body are visible there.

## Endpoint requirements

- `https://` only. `http://`, `localhost` and private ranges are rejected.
- The address is re-checked before every send, not just when you save it.
- A disabled endpoint is not called; the attempt is logged as `skipped_inactive`.
